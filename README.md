# Local LLM Coding Benchmark: Core i7-4790K + 32 GB DDR3 + RTX 4060 (8 GB)

Практические результаты двухдневного стресс-теста локальных моделей **Qwen (`9B`, `27B Dense`, `30B-A3B MoE`)** в связке **Ollama + VS Code (Cline)** на платформе 2013–2014 года (Haswell, DDR3) с современной видеокартой **NVIDIA RTX 4060 8 GB**.

Главная цель эксперимента — найти реальный физический предел контекстного окна (`32K → 64K → 128K → 256K`) при гибридном вычислении (`GPU + CPU/DDR3`) и выработать правила работы AI-агента, при которых локальные модели не «забывают» код и не ломают крупные Python/PyQt6-проекты.

---

## 1. Конфигурация тестового стенда

* **CPU:** Intel Core i7-4790K (4 ядра / 8 потоков, 4.0–4.4 GHz)
* **RAM:** 32 GB DDR3 (Dual Channel)
* **GPU:** NVIDIA GeForce RTX 4060 8 GB GDDR6 (Resizable BAR включён)
* **Storage:** Системный NVMe SSD (Windows 11) + SATA HDD для хранения весов моделей
* **Runtime:** Ollama (Desktop / CLI) + расширение **Cline** в VS Code

---

## 2. Критически важные настройки Ollama (без них большой контекст не взлетит)

Чтобы уместить большие контексты (`128K–256K`) в 8 GB VRAM + 32 GB RAM без потери точности и вылета в файл подкачки, в Windows необходимо задать две переменные окружения и **полностью перезапустить Ollama**:

```cmd
setx OLLAMA_FLASH_ATTENTION 1
setx OLLAMA_KV_CACHE_TYPE q8_0
```

* `OLLAMA_FLASH_ATTENTION=1` — включает оптимизацию внимания Flash Attention, резко снижая расход памяти под длинный контекст и ускоряя обработку промпта.
* `OLLAMA_KV_CACHE_TYPE=q8_0` — сжимает KV-кэш контекста в 8-битный формат с минимальной потерей качества, позволяя удвоить окно контекста в том же объёме памяти.

*(Также в настройках самого приложения Ollama ползунок **Context length** и параметр **Model Context Window** в Cline должны быть выставлены синхронно).*

## 4. Практические выводы по выбору моделей для Cline

1. **Золотой стандарт контекста для 32 GB RAM — `128K` (`131072`):**
   * На `128K` полностью исчезает автосжатие истории в Cline (`Auto-compacting context`), из-за которого локальные модели чаще всего начинают галлюцинировать и дублировать код.
   * При этом в системе остаётся 3.5–4 ГБ свободной ОЗУ, и Windows не уходит в файл подкачки.
   * Разгон до `256K` на 30B MoE технически возможен (98% ОЗУ), но пропускная способность двухканальной DDR3 становится узким горлышком.
2. **Распределение ролей между моделями:**
   * **`qwen3.6:27b` (128K)** — «главный архитектор». Не самая быстрая, но единственная, кто самостоятельно проверяет `git show`, находит дубликаты методов, вычищает чужие ошибки импортов и доводит сложный многофайловый рефакторинг до чистой компиляции.
   * **`qwen3-coder:30b-a3b` (128K)** — «скоростной кодер». За счёт архитектуры MoE печатает значительно быстрее плотной 27B; требует увеличенного `Request Timeout (ms)` в Cline (1 200 000 мс / 20 минут) на тяжелых файлах.
   * **`qwen3.5:9b` (128K)** — «спринтер». Идеальна для точечных правок на 20–50 строк, написания `docstrings` и черновой нарезки кода, но на сложных зависимостях требует жёсткого контроля.

## 5. Главный лайфхак ускорения: правило 500 строк и паттерн Mixin

Главная причина зависаний локальных моделей в Cline — не нехватка VRAM, а **монолитные файлы длиннее 500–1000 строк**. Когда модель пытается применить `SEARCH / REPLACE` к файлу на 1600 строк, она либо упирается в лимит длины одного ответа (`Max Output Tokens`), либо тратит 10–15 минут на генерацию одного `diff`.

**Рабочее решение для Python / PyQt6:**
1. Разбить все файлы `> 500` строк на компактные модули по **200–450 строк** с помощью **классов-миксинов (`Mixin`)**.
2. Главный класс окна наследует эти миксины, сохраняя 100% обратную совместимость и доступ ко всем атрибутам `self.*`.
3. В файлах `.clinerules` запретить модели перезаписывать длинные файлы целиком за один вызов.

Пример готового шаблона правил см. в файле [`.clinerules.example`](.clinerules.example).
